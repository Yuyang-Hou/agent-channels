# Pijoo 产品方向草案

> 状态：P0 已进入实现；本文件记录产品范围，正式行为契约仍以 OpenSpec 为准。

## 产品主线

这些方向不应作为多个平行项目推进。登录实现前，P0 先收敛为一条首次成功链路：

```text
首次打开
  -> 自动生成可编辑的本机昵称
  -> 进入频道界面
  -> 用户选择“连接 AI 会话”
  -> 检查并配置 Codex MCP / Skill
  -> 完全重启 ChatGPT，确认当前版本 MCP 已加载
  -> 连接已有 AI 会话或创建专属会话
  -> 收到第一条真实频道消息
```

核心目标：让新用户在五分钟内完成一次真实的“频道消息进入 AI 会话”。

登录、私人欢迎频道、好友和模板在后续阶段接到这条链路上，不阻塞当前 P0。

## 推进顺序

| 阶段 | 方向 | 首版目标 |
|---|---|---|
| P0 产品可用 | macOS 主文件拆分、默认昵称、Codex 集成门禁、实时消息、休眠恢复 | 降低改动风险，消除进入阻塞、无效试错和静默丢消息感 |
| P1 身份社交 | GitHub 登录、好友频道、私人欢迎频道 | 建立稳定用户、设备和好友关系 |
| P2 增长实验 | 内置频道模板、AI 狼人杀、模板分享 | 验证模板是否降低创建门槛并带来传播 |
| P3 平台化 | 公开模板社区、复杂游戏能力 | 只在真实使用量和治理能力出现后建设 |

## P0：先补齐产品可用性

### P0-0：macOS 主文件机械拆分

#### 现状评估

`macos/PijooApp.swift` 当前约 5751 行，已经不只是格式问题：

- 约 2300 行同时包含领域模型、纯函数、配置编辑、日志、Keychain、Skill/MCP 安装、本机 socket、更新、Sidecar 和消息账本；
- `AppModel` 及其 extension 约 1800 行，同时编排频道、成员、邀请、会话、Subscription、Host 投递、SSE、Codex 集成和设置；
- SwiftUI 页面约 1200 行；
- 自测与正式 `@main` 入口仍在同一个文件；
- `build-app.sh` 和 focused self-test 都只显式编译这一个 App 源文件。

P0 的默认昵称、Codex 门禁、实时同步和恢复确认都会修改这个文件的不同区域。继续叠加会增加冲突、误改和验证成本，因此在行为开发前先做一次可独立验证的机械拆分。

#### P0 拆分边界

首轮只拆成少量职责文件：

```text
macos/
  PijooApp.swift          # AppDelegate 与正式 @main 入口
  PijooModels.swift       # 状态模型、消息模型、纯函数和模板渲染
  PijooServices.swift     # 路径、日志、Keychain、账本、Sidecar、安装器和本机 socket
  PijooAppModel.swift     # AppModel 状态与现有业务 extension
  PijooViews.swift        # 菜单栏、主窗口、频道、会话和设置 UI
  PijooSelfTest.swift     # 现有 SELF_TEST 入口与断言
  UpdateHelper.swift      # 保持不变
```

同时在 `build-app.sh` 定义一份显式 App 源文件列表，正式 App 和 focused self-test 共用，避免两条编译路径漏文件。

#### 明确不做

- 不改状态文件、Keychain、HTTP、MCP、本机 socket 或消息协议；
- 不把 `AppModel` 重写成多个新架构层，也不引入依赖注入框架；
- 不增加 Swift Package、Xcode 工程或第三方依赖；
- 不趁拆分重命名大量模型、整理所有访问级别或重写并发逻辑；
- 不处理服务端 `app.ts`，P0 只解决会被本轮功能集中修改的 macOS 主文件。

如果拆分后 `PijooAppModel.swift` 仍频繁产生多人冲突，再按 `Channels`、`Subscriptions`、`Codex` 拆 extension；首轮不提前拆成十几个文件。

#### 执行和验收

机械拆分优先作为独立 diff 审核边界；是否提交由产品明确授权，不能为了拆分擅自提交或发布。

验收要求：

- App 源码行为零变化，现有本地状态无需迁移；
- focused Swift self-test 继续通过；
- App-only 编译通过，内嵌 Skill、Sidecar 和版本信息不变；
- `git diff --check` 通过；
- 不扩大为 `public` API，只使用同一可执行模块内必要的默认访问级别；
- 拆分完成后，默认昵称、Codex 门禁、实时同步和恢复确认分别保留清晰的 diff 边界与对应检查。

### 默认本机昵称

P0 暂不依赖登录。首次启动且本机没有昵称时，App 自动生成一个稳定的默认昵称，例如
`Pijoo用户-7K3M2Q`：

- 后缀使用本机首次启动时生成的 6 位随机字符，不读取系统用户名、设备序列号或其他隐私标识；
- 生成后写入现有本机状态，重启和升级不重新生成；
- 用户可以随时在设置中修改；
- 默认昵称只是显示名称，不作为身份、鉴权或防重复依据；
- 有了默认昵称后直接进入频道界面，不再用“昵称为空”阻塞首次使用。

### Codex 集成与绑定门禁

Pijoo 的主要价值依赖 Codex MCP / Skill，因此频道浏览可以开放，但所有“连接 AI 会话”的入口必须先通过集成检查，避免用户在尚未重启 ChatGPT 时反复搜索、创建或绑定会话。

复用现有配置检测和 `mcp_ready` 版本上报，统一为四种用户可见状态：

| 状态 | 判断 | 允许的操作 |
|---|---|---|
| 未配置 | MCP 配置或 Skill 缺失 | 可使用 App 频道；禁止搜索、创建、绑定 AI 会话；显示“配置 Codex 集成” |
| 待重启 | MCP / Skill 已写入，但未收到当前 App 版本的 `mcp_ready` | 禁止搜索、创建、绑定；显示“完全退出并重启 ChatGPT” |
| 版本不符 | ChatGPT 上报的 MCP 版本不是当前 App 版本 | 禁止搜索、创建、绑定；显示已加载版本和当前版本，并引导修复后重启 |
| 可连接 | MCP / Skill 已配置，且当前版本 MCP 已上报 | 开放会话搜索、创建、预检和绑定 |

具体交互：

- 用户第一次进入“转发到会话”时，在原位置显示阻塞说明和唯一下一步，不跳转到空搜索结果；
- 配置完成后明确说明需要“完全退出 ChatGPT”，不是只关闭窗口；
- 待重启时不提供“继续绑定”或“忽略并继续”；
- App 收到当前版本 `mcp_ready` 后自动解除门禁，不要求手动刷新；
- 如果重启后仍未确认，提示用户打开任一 Codex 会话，让 ChatGPT 加载集成；
- 创建频道、加入频道、App 内收发和查看历史不受 Codex 门禁影响。

### 会话休眠与错过消息恢复

P0 恢复机制区分三种状态：

1. **App 与 Host 正常**：通过 SSE 实时投递。
2. **短暂断网或正常连接续接**：频道 feed 与 Subscription 都从持久 cursor 续接，本地按频道和消息 ID 去重，成功恢复后继续自动投递。
3. **系统长时间休眠**：消息先记录为本机待恢复，唤醒后必须由用户确认，不能自动创建 turn。

“恢复待确认”以现有 Subscription 为单位：

- 系统休眠超过 60 秒时进入恢复模式；普通网络重连仍走现有自动续接；
- 恢复模式下先把积压消息写入本地 ledger，并暂停该 Subscription 的 Host 投递；
- App 显示休眠期间待检查的 Subscription 投递数量；
- `查看消息` 只打开 App 历史，不创建 turn；
- `发送到会话` 是唯一会创建恢复 turn 的操作；确认后复用现有 Subscription 顺序与普通模板；
- `暂不发送` 保留待确认状态，用户之后仍可处理；
- 等待用户决定期间的新消息继续显示在 App，并加入同一待确认队列，避免越过旧消息造成顺序错乱；
- 用户同意后若 Host 投递失败，继续保留待恢复；结果未知时暂停且不自动重试。

正常在线、短于 60 秒的系统休眠和网络抖动继续自动投递，不应频繁打断用户确认。首版不做积压合并总结；如果真实使用中出现一次恢复创建过多 turn，再增加确定性的批量恢复卡片。

当前服务端只保留每频道最近 100 条内存消息，超过窗口的缺口提示尚未实现。账号版迁入 PostgreSQL 后，可先采用“7 天或每频道 1000 条，先到为准”的短期保留，并补上明确的缺口提示。

### 消息实时同步

目标是像即时通信 App 一样：只要 Pijoo 处于可运行状态，不论用户当前查看哪个频道、窗口是否在前台，都持续收到最新消息；重新进入频道不应成为触发刷新的必要条件。

消息同步采用“在线长轮询 + 生命周期补齐”，不增加固定间隔短轮询：

- 每个已加入频道维持一个独立长轮询 feed，不能依赖当前选中频道；
- 消息到达后请求立即返回，App 写入本地 ledger、更新未读数，并开始下一轮监听；
- App 启动、从系统休眠恢复、网络恢复和重新进入前台时，拉取服务端完整保留窗口并按本地消息 ID 补齐所有频道；
- 每轮长轮询显式携带本地 cursor，不能只依赖服务端进程内 cursor；
- 频道切换只读取本地 ledger，不再承担“触发最新消息”的职责；
- 保留手动刷新作为诊断兜底，但正常用户不需要使用；
- 删除频道选择和消息视图产生的重复 history 请求，并行刷新成员、邀请等互不依赖的数据。

优化前后记录三个时间点：

- 服务端接受消息时间；
- App 收到在线 feed 时间；
- UI 完成展示时间。

首版验收目标：

- 在线消息展示 P95 小于 1 秒；
- 短暂断线后的恢复小于 3 秒；
- App 停留在其他频道或窗口隐藏时，消息同样实时进入本地历史并更新未读；
- App 恢复前台时无需切换频道即可补齐；
- 同一消息不会因在线 feed、前台补齐或频道切换而重复显示。

## P1：登录与好友关系

### GitHub 登录

沿用现有 `add-github-account-system` 设计：

- 首版仅提供 GitHub OAuth authorization code + PKCE；
- GitHub 只证明稳定 user id，Pijoo 签发自己的不透明 Session；
- App 不持有或持久化 GitHub token；
- 新设备恢复云端 Membership，不同步本地消息、TaskBinding、Subscription、Host 会话 ID 或工作目录；
- 实施前只读检查线上是否已有真实用户，决定 clean-slate 还是单独设计一次性认领。

GitHub 登录适合当前研发用户。如果游戏和社区后续面向普通消费者，再根据真实用户来源增加 Apple 或 Google 登录，不提前建设通用身份框架。

### 好友与好友频道

首版复用现有 Channel，不建设第二套私信协议：

- 用户通过单次好友邀请链接添加好友；
- 对方接受后建立 Friendship，并创建或复用一个仅两人的私有 `direct` Channel；
- 好友列表只是关系和这些频道的索引；
- 好友频道仍可连接多个本机 AI 会话，继续使用现有 Subscription；
- 必须同时支持删除好友和屏蔽；屏蔽后不能发送、邀请或重新建立好友关系。

首版不做公开用户搜索、好友推荐、通讯录同步、动态广场或复杂分组。

### 私人欢迎频道与 Welcome Bot

每个账号拥有一个仅包含自己和 Welcome Bot 的“Pijoo 入门”频道，不把所有新人放进同一个公开频道。

Welcome Bot 首版是确定性服务，不需要 LLM：

- 账号创建时幂等加入欢迎频道；
- 只发送一次欢迎介绍；
- 引导连接已有会话或创建专属会话；
- 连接成功后发送第一条真实测试消息；
- 提供邀请好友和从模板创建频道的下一步入口。

这样新手引导本身也会验收频道、App、Subscription 和 Host 投递链路。

## Skill 与动态数据

官方 Pijoo Skill 保持公开可读并由 App 管理。用户自定义内容通过消息模板和未来的频道模板承载，不直接修改官方 Skill。

- 已加入频道继续通过 `list_channels` 动态读取；
- 好友能力完成后增加只读 `list_friends`，或者让 `list_channels` 返回 `kind=direct`；
- 不把频道和好友列表注入每个 turn，也不把它们做成静态模板变量；
- 消息模板变量继续只描述当前消息，例如频道、发送者、提醒范围和消息 ID；
- 只有用户或 Agent 真正需要选择频道、好友时才读取动态列表。

## P2：模板与游戏增长实验

先建设频道模板，不建设游戏 SDK、脚本运行平台或嵌入式应用容器。

第一批内置模板：

- 前后端协作；
- AI 代码评审；
- AI 圆桌讨论；
- AI 狼人杀。

首版模板只包含：

- 频道名称与介绍；
- 推荐 Human、Agent 和会话数量；
- Welcome Bot 初始消息；
- 默认提醒与接收策略；
- 用户主动创建专属会话时可见的初始提示词。

AI 狼人杀首先作为可传播的产品演示，用来验证多用户、多 Agent、多轮消息和模板创建体验，不作为底层架构。

模板验证顺序：

1. App 内置少量官方模板；
2. 支持分享链接或 JSON 导入；
3. 验证模板创建率、好友加入率和首轮完成率；
4. 有真实供给和使用量后，再建设公开社区、作者、版本、审核、举报和下架机制。

## 验收指标

- `PijooApp.swift` 只保留入口，P0 功能不再继续堆入单一主文件；
- 机械拆分前后状态、协议和用户行为一致；
- 新安装到第一条消息进入 AI 会话：五分钟以内；
- 首次启动自动生成稳定且可编辑的本机昵称；
- Codex 未配置、待重启或版本不符时不能搜索、创建或绑定 AI 会话；
- 当前版本 MCP 上报后门禁自动解除；
- 频道消息不依赖重新进入频道或手动刷新；
- 休眠积压必须经用户确认才创建恢复 turn；
- 保留窗口内的恢复没有静默丢失或重复 Host turn；
- 接受好友邀请后，一步进入可用的双人频道；
- 从模板创建频道到开始第一轮互动：两分钟以内。

## 暂不建设

- 独立私信或聊天协议；
- 通用身份提供方框架；
- 动态频道、好友数据的每 turn 注入；
- LLM 驱动的新手 Bot；
- 游戏 Runtime、插件市场或工作流 DSL；
- 没有审核和滥用治理的公开模板发布。
